# Discover and shape

For product goals, priorities, linked scope, and current roadmap facts, use [the product workflow](product.md). Read it when product state exists or this stage changes a product decision.
Read the shared protocol. Use the [brief template](../../../templates/product-brief.md) when it helps.

Capture the target user, situation, problem, existing alternative, and desired outcome. Extract the user's stated constraints before asking questions. Do not ask for a preferred stack when it does not yet affect the product decision.

Separate direct evidence, observed repository behavior, sourced research, and assumptions. Give each source an ID. Record source date and limits in its reference or linked brief. A generated persona or interview is a hypothesis, never user evidence.

For a new idea:
- Compare the smallest viable options for the main user task.
- State the first audience, first useful result, and non-goals.
- Identify the most consequential uncertainty: demand, usability, feasibility, distribution, cost, or legal context.
- Propose or perform the cheapest authorized test of that uncertainty.
- Define a success measure, a measurement window, and a keep/change/stop rule.
- For a business, include acquisition, pricing hypothesis, onboarding, support, and unit cost.

For an existing product, use actual feedback and telemetry when available. Inspect the baseline before proposing a rewrite. Keep observations distinct from inferred intent.

Validate: Can the user explain the first version? Does the chosen test address the largest unknown? Are evidence limits visible? Is success linked to user value? A market or user test that has not run remains open.

Output a compact brief and one bounded change proposal. A short user request can justify a short brief. Use real research only when relevant; do not start a broad research project for a small fix. Do not send recruitment or marketing material without authority.
